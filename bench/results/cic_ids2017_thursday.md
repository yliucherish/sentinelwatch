- PCAP：`D:\Downloads\Thursday-WorkingHours.pcap`（7.7 GB，时间跨度 2017-07-06 20:01:18 ~ 2017-07-07 04:04:27）
- 数据来源：https://cicresearch.ca/CICDataset/CIC-IDS-2017/ → PCAPs/Thursday-WorkingHours.pcap
- 标注口径：`time_window+src_ip` —— 落在攻击时间窗**且**源 IP 为攻击源 IP 的请求记为应检出，其余记为应放行
- 备注：CIC 的标签按 flow 打，本工具按 HTTP request 产出事件，所以不用自带标签，改用「时间窗 + 攻击源 IP」对齐。攻击者 IP 在非攻击时段也有正常流量，故必须时间窗与 IP 同时匹配才算攻击。标注窗的边界误差不试图靠调整窗来掩盖，而是由 attacker_ips 统计窗外的攻击机请求，在报告里给出检出率的上界（见 BENCHMARK.md）。

> ⚠️ 数据集标签通常是**按流**打的，本工具产出的是**按请求**的事件。两者粒度不同，所以本报告不使用数据集自带的 flow 标签，而是用「时间窗 + 攻击源 IP」这个显式口径对齐。**口径写在上面，别人可以照着复核**——这是这份报告能被采信的前提。

## 检出率为什么是这个数：分母构成

主口径把「攻击机在攻击时段发出的**每一次** HTTP 请求」都标为应检出。
但签名检测按设计只对**载荷**告警，而一个攻击时段的请求里，大量是打开页面、加载 CSS、提交登录表单这类**不含注入载荷**的请求。它们进了分母，检出率就被稀释。下面按 URI 语法分层：

| 标注 | URI 查询参数 | 请求数 | 命中 | 命中率 |
|---|---|---|---|---|
| 应检出 | 无 query | 8062 | 0 | 0.00% |
| 应检出 | 有非空 query | 863 | 853 | 98.84% |
| 应放行 | 无 query | 33774 | 1 | 0.00% |
| 应放行 | 有非空 query | 13411 | 41 | 0.31% |

> 「有非空 query」是**纯语法判据**（URI 里 `?` 后面有没有内容），不是「能被我的规则匹配」，也不是一个新的检出率口径。它只回答一个问题：分母里混进了多少无载荷请求。上表不替换主指标，只解释主指标；把两列分开印，是为了让读的人自己判断这个检出率能不能代表能力。


## 参与判定的规则

只统计**签名规则**（单条请求即可判定），且只列 `event_types` 与本次数据（http_request）有交集的规则——只吃应用日志的规则对流量永不命中，列进来纯属误导。

阈值规则（窗口聚合）没有进混淆矩阵：一次爆破的 5 条失败请求无法逐条标注"哪条该告警"，粒度不同不能混算。

- `http-log4shell-jndi`（critical）— 流量侧 Log4Shell JNDI 注入（CVE-2021-44228）
- `http-fastjson-autotype`（critical）— 流量侧 Fastjson autoType 反序列化载荷
- `http-webshell-body-markers`（critical）— 流量侧 WebShell 落地特征
- `http-sqli-union-select`（critical）— 流量侧 SQL 注入（UNION 联合查询）
- `http-sqli-boolean-blind`（high）— 流量侧 SQL 注入（布尔盲注）
- `http-sqli-time-based`（high）— 流量侧 SQL 注入（时间盲注）
- `http-sqli-metadata-probe`（high）— 流量侧 SQL 注入（元数据/文件探测）
- `http-xss-script-injection`（high）— 流量侧 XSS（脚本标签注入）
- `http-xss-event-handler`（medium）— 流量侧 XSS（事件处理器注入）
- `http-path-traversal`（high）— 流量侧 路径遍历

## 标注灰色地带

- 落在攻击时间窗内、但源 IP 不是攻击源的请求：**8431 条**（占全部 56110 条的 15.03%）

  这类请求被记为「应放行」。它们可能是同网段的正常用户，也可能是数据集按 flow 标注导致的漏标。**把它印出来而不是藏起来**，是因为它直接决定了误报率的分母是否干净——读的人有权知道。

- 来自攻击机（`172.16.0.1`，抓包点 NAT 后的地址）但落在所有攻击时间窗之外的请求：**287 条**，其中 41 条被规则命中

  论文给的攻击时段四舍五入到整十分钟，而 SQLi 窗只有两分钟宽，所以标注窗必然有边界误差。这些请求被记为「应放行」，检测器若命中反而计入误报。把窗放宽到「攻击机的流量一律算攻击」，检出率上界为 **9.70%**（主口径 9.56%）。两个数都给出，是因为单独任一个都在替读者做判断。

  推论：本轮 42 条 FP 里有 41 条是上述边界外溢，**真正来自非攻击源的误报是 1 条**。把标注误差和检测器误差混成一个 FP 数字，会同时冤枉检测器和高估数据集。
