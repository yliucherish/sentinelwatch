|---|---|---|
| `crosscheck_bypasslab.md` | bypasslab 228 条（含 OWASP CRS 59 条第三方基准、冻结 holdout 19 条） | 检测范围内 150/184 = **81.5%**（SQLi 94.0% / XSS 81.2% / 路径遍历 100.0% / 反序列化 93.3% / **命令注入 53.1%** / **SSRF 94.4%**）；良性 36 条误报 1 条；**只剩扫描器指纹 8 条不进分母**——UA 判据精度 0/80 不开；v2.2 换的路径判据（§2.12）精度好得多，但这 8 条样本只有 `GET /` + UA，路径上无从下手 |

> 这份报告的作用不是给检测器打分，而是**定位规则烂在哪一层**：
> v1.8 首测把「归一化缺口（`+` 未解码，58/117）」和「规则覆盖缺口」分开量化；
> v1.9 修掉归一化后是 65/117 = 55.6%，`crs` 子集仍是 12/59——说明剩下的确实
> 是判据形态问题；v2.0 把判据从「枚举写法」改成「描述形状」后到 **107/117**，
> `crs` 子集 **27/59**，未参与调参的 holdout 冻结集 **11/19**；
> v2.1 补上命令注入与 SSRF 判据，**分母从 117 涨到 184**，150/184 = 81.5%
> （`crs` **32/59**、holdout **15/19**）——总分降了但**不是退步**，是同分母
> 四列（SQLi / XSS / 路径遍历 / 反序列化）一条没掉。见 §2.11。
> v2.2 换了一个判据维度抓扫描器（「扫什么路径」而不是「自称谁」），真实流量上
> 0 误报、8 条真探测，但**没上线**（会拖累标注口径下的误报数，而唯一能抵消的
> 办法是改标注）；判据与测量留在 `bench/proposed/`，见 §2.12。
>
> **v1.9、v2.0 都重新生成了全部七份报告**，因为归一化与判据改动影响了
> 逐请求与交叉评测的数字（周四 TP 853 → 855 → 857，FP 一直 42）；窗口级三份
> 在两轮之后都与 v1.7 完全一致（8 告警 8 TP / 0 FP）——`uri` 判据不经过
> `normalized` / `sql_view`，按预期应当不变，实测确认。

> 的行）上一次都没命中——矩阵一个数都没变，重跑只会产出同样内容的文件。
> 这个结论是实测的：拿 `bench/.cache/` 把 `attack=true` 的行也过了一遍。

下面这份由 `bench/run_crs_bench.py` 产出（v2.3），是**第三方外部基准**：直接把
OWASP CRS 的全量回归测试集（148 个规则文件 / 2,503 条用例）转成语料，测本项目的
签名规则。它既不是真实流量、也不是自造载荷，口径与前几组都不同，见
[`BENCHMARK.md`](../BENCHMARK.md) §2.13：

| 文件 | 语料 | 主要结论 |
|---|---|---|
| `crs_regression.md` | OWASP CRS 全量回归集 2,503 条（1,940 条该检出 / 563 条「不该触发本规则」） | **313/1,940 = 16.1%**（SQLi 20.3% / XSS 20.1% / 路径遍历 22.4% / **命令注入 10.0%**）；零命中规则族 **87/148**；漏检归因：**41% 的漏检集中在三组「CRS 判危险词、我们判注入语法结构」的规则族上** |

> 这份报告的价值不在于那个百分比，在于**它把 59 条时的 54.2% 打回了 16.1%**。
> 手抄的 59 条挑的是四个 libinjection 方法文件，形状最接近正则，数字偏乐观是
> 挑样本的必然结果。扩到全量之后：
> - **两种判据范式分开报**：排除 CRS 的字符频率计分族（`94243x`）后是 16.1%
>   ——**一分不差**，说明差距不在那三条规则上，这是个有用的否证；
> - **不做「误报率」**：那 563 条 `no_expect_ids` 是**规则维度**的期望，不是良性
>   标签，里面混着 `'||(select(pg_sleep(15))where(true))||'` 这种真注入。
>   第一版把它当良性，报出「误报 4.44%」——一个方向完全指反的指标；
> - **漏检按规则族归因**：`932140`（Windows FOR/IF，154 条全灭）、
>   `932236/932235/932239/932260`（Unix 命令词检测）、`942120/942151/942410…`
>   （SQL 算子/函数名检测）三组占了 41%，其余 130 多个规则族各自只有个位数。

## 为什么只有报告，没有逐请求 CSV

`out/bench_*.csv` 是逐请求明细，三份合计约 21 MB，包含数据集里的真实 URI 与
主机头。它们由 `.gitignore` 排除，不进仓库——需要的人用下面的命令自己生成，
比下载一个可能过期的二进制产物更可靠：

```bash
python bench/run_benchmark.py --pcap <pcap> \
    --labels bench/labels/<对应标注>.json --out out/
```

标注文件在 `bench/labels/`，偏移与攻击源 IP 的实测依据写在各文件的
`_offset_evidence` / `_attacker_ip_note` 字段里。

## 报告里的路径

报告首行**只写 PCAP 文件名**（如 `Thursday-WorkingHours.pcap`），不写完整路径。
v1.9 之前这里打印的是运行时绝对路径（本机 `D:\Downloads\` 与 `data/`），等于
把开发机的目录结构永久写进 git 历史；现在两个评测脚本都改成只取文件名。
换任何路径都能复现，只要文件字节一致。

复现命令、口径定义与局限清单见 [`BENCHMARK.md`](../BENCHMARK.md)。
