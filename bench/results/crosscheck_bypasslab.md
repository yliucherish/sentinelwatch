# 跨项目交叉评测：bypasslab 语料 × sentinelwatch 规则

- 语料：`corpus_full.json`（228 条样本；由 bypasslab 的 `go run ./cmd/export` 生成）
- 参与评测的签名规则：20 条；另有 3 条窗口/阈值规则未参与（见下方口径）

> ⚠️ **两条口径，缺一条数字就不可信**：
> 1. 只测**签名规则**。`threshold > 1` 的窗口规则要多次事件才成立，单条样本无法评测——它们不参与本报告，**不等于漏检**。
> 2. **能力边界不计入分母**：本工具没有 RCE / SSRF 规则，这两类记`unsupported` 并排除在检出率之外。把「没有这个能力」算成 0% 命中，是拿分母惩罚自己。

## 根因归因：缺口分三类，性质完全不同

### 1. 归一化缺口：`+` 未按 form 编码还原成空格（v1.9 已修）

v1.8 首次评测时发现的缺口：`normalize()` 只做 `unquote()`（URL 解码到不动点）再转小写，**不处理 `+`**。但 query string 和 `application/x-www-form-urlencoded` 的 body 里，`+` 的语义就是空格——`id=1+UNION+SELECT+...` 是最常见的注入写法之一，归一化后仍是 `1+union+select`，规则里的 `union select` 自然匹配不到。**form 编码因此成了一种天然的绕过语法**，而且不需要攻击者懂任何漏洞。

v1.9 已修（`collectors.pcap._judgement_text()`）：只对请求行的 query 部分和 Content-Type 为 form-urlencoded 的 body 做 `+`→空格，且**必须在 unquote 之前**做（否则 `%2B` 这个真正的加号会先被解码成 `+`、再被误换成空格）。`raw` 一个字没动——判据可以归一化，证据不能。

修订前后（同一份语料、同一套规则，只差归一化这一步）：检测范围内 **49.6%（58/117）→ 55.6%（65/117）**；SQLi 从 **16/50 → 23/50**。一条规则都没改，救回来的全是同一语义的另一种编码。

### 2. 规则覆盖缺口：无引号恒真式、非 UNION 形态（要加规则）

例如 `1234 OR 1=1`（`CRS-942100-01`）：`http-sqli-boolean-blind` 只认带引号的 `' or '1'='1` 形态。这是判据覆盖面问题，不是编码问题——加规则能解，但要看误报代价。

### 3. 能力缺口：RCE / SSRF 没有规则（不是漏检）

`rce` 49 条、`ssrf` 18 条攻击样本**全部不计入分母**。这是没有这个检测能力，不是「检出了 0%」。真要补，属于新增检测面（命令注入/SSRF 特征），不是改现有规则。
