## 1. 评测口径（先定口径，再看数字）

数据集标签按 **flow** 打，本工具产出按 **HTTP 请求** 的事件。粒度不同，硬对齐
会算错。所以评测不使用数据集自带标签，而用显式声明的口径：

```
落在某攻击时间窗内 且 源 IP 为该窗的攻击源 IP  → 应检出（positive）
其余请求                                        → 应放行（negative）
```

两个条件缺一不可。只按 IP 判会把攻击者在非攻击时段的正常流量算成攻击，人为
抬高检出率；只按时间窗判会把同网段正常用户算成攻击，人为抬高误报率。

**只有签名规则进混淆矩阵。** 阈值规则（窗口聚合）是另一个粒度：一次爆破的
5 条失败请求，无法逐条标注"哪条该告警"。混进来算，指标就没有意义了。
v1.7 新增的频次规则因此**另出一份告警级评测**（§2.6），不进本矩阵。

### 1.1 三个必须先实测才能填的标注参数

这三个值看着像配置，其实都是从字节里量出来的结论。任何一个填错，症状都是
「检出率 0%」，与「检测器坏了」长得一模一样：

| 参数 | 值 | 怎么量出来的 |
|---|---|---|
| `pcap_time_offset_hours` | **3** | 论文时段是 ADT（UTC−3），PCAP 是 UTC epoch。周二 FTP-Patator 论文止点 10:20 ↔ 实测 SYN 突增段止点 13:20 UTC；整天抓包 11:53–20:00 UTC = 08:53–17:00 ADT，正好办公时段 |
| 攻击源 `src_ips` | **`172.16.0.1`** | 抓包点在防火墙内侧，文档里的公网攻击机 `205.174.165.73` 被 NAT 改写，在 pcap 里一条都没有。周二 48,345 条 HTTP 请求源 IP 全是 `192.168.10.x`，而端口 21 的 3,978 个 SYN 全来自网关 |
| 窗口比较基准 | **epoch** | 标注窗按 UTC 解释后换算 epoch，事件的本地 naive 时间用 `.timestamp()` 还原 epoch；两侧与运行机器时区无关。见 §3.4 |

复核工具：`python tools/probe_window.py <pcap> 21 22`（按分钟统计目标端口 SYN，
打印突增段的 UTC 与 EDT 墙钟时间）。证据与推理详见 [`DATASETS.md`](DATASETS.md)。

## 2. 结果

### 2.1 脚本自检（合成样本 ✅）

这不是数据集结果，是"评测脚本本身对不对"的证明。用 `tools/pcapgen.py` 的
演示样本，标注为「2 条正常 + 3 条攻击」：

```bash
$ python bench/run_benchmark.py --self-test
  事件 5 条：TP=3 FN=0 FP=0 TN=2
  检出率 100%，误报率 0%
[+] 自检通过
```

自检还会在 UTC / 上海 / 纽约 / 柏林四个时区各跑一遍（CI 的 `bench-timezone`
矩阵），因为标注错位这类 bug 在开发机上是看不出来的。

### 2.2 解析器吞吐标定（合成样本）

`tools/bench_throughput.py` 给出 15.0 MB/s（每条请求独立五元组，专测最坏情况下
的建流开销）。真实流量按字节算快得多，因为大量是非 HTTP 包：

> 两个数都对，但含义不同：合成样本测「最坏情况的建流开销」，真实数据集测
> 「这一天的流量组合」。别把 15 MB/s 当成产品性能，也别拿 400 请求/s 当瓶颈——
> CIC 这一天平均约 390 个包才出一条 HTTP 请求，瓶颈在读包。

```
真实误报 = 3（周一） + 0（周二） + 1（周四） = 4 条
```

### 2.4 检出率 9.58% 为什么不是「检测器不行」

主口径把「攻击机在攻击时段发出的**每一次** HTTP 请求」都标为应检出。周四窗内
8,925 条里，绝大多数根本不含注入载荷：

| 应检出的请求 | 条数 | 命中 | 命中率 | 都是些什么 |
|---|---:|---:|---:|---|
| URI 无 query | 8,062 | 0 | 0.00% | 5,385 次 `POST/GET /dv/login.php`（凭据爆破）、2,656 次**空的** `GET /dv/vulnerabilities/xss_r/`、CSS/favicon |
| URI 有非空 query | **863** | **855** | **99.07%** | `%3Cscript%3Econsole.log(...)%3Bconsole.log(document.cookie)` 等真实 XSS 载荷、SQLi 探测串 |

签名检测按设计只对载荷告警，8,062 条无载荷请求进了分母，检出率自然被压到个位数。
**「有非空 query」是纯语法判据**（URI 里 `?` 后面有没有内容），不是「能被我的规则
匹配」，也不是另造一个更漂亮的分母。它只回答一个问题：分母里混进了多少无载荷
请求。分层表**不替换**主指标，只解释主指标；两个数都印出来，读者自己判断。

报告里的「分攻击类型」表则是**按标注时间窗**归类（不是按 URI 内容归类）：

| 时间窗 | 请求 | 命中 | 说明 |
|---|---:|---:|---|
| Brute Force 09:20–10:00 | 7,181 | 0 | 表单爆破没有载荷特征，见 §3.6；v1.7 的窗口级补强见 §2.6 |
| XSS 10:15–10:35 | 1,735 | 850 | 窗内混着大量空 `xss_r/` 页面 GET |
| SQLi 10:40–10:42 | 9 | 5 | 窗只有 2 分钟宽，边界误差最敏感；v1.9 的 `+` 解码在这里多抓到 2 条（3 → 5） |

### 2.5 那 4 条真误报：归一化带来的固有张力

四条误报是**同一个模式**，周一 3 条 + 周四 1 条，可逐包复现：

```
POST http://logs.clrsrv.com/ar.logger.php HTTP/1.1
origin: http://www.cosmopolitan.com
content-type: application/x-www-form-urlencoded
content-length: 18856

param=%7B%22AdId%22...%22adm%22%3A%22%3Ciframe%20src%3D...   ← URL 编码的广告素材 HTML
```

浏览器正常浏览页面时，广告 SDK 把**竞价日志**（`BidPartners` / `indexExchange` /
`adm`）用 URL 编码 POST 到日志服务器，`adm` 字段里带 `<iframe>` / `<script>`
形式的广告创意 HTML。归一化把它解到不动点之后，XSS 规则看到了脚本标签，报了警。

这里有个绕不过去的张力：

- **不归一化** → `%3Cscript%3E` 直接绕过，真 XSS 全漏；
- **归一化** → 被合法编码的第三方富文本看起来就像攻击。

调阈值解决不了，给 `/ar.logger.php` 加白名单更是把这个数据集背下来了——换一家
广告平台立刻复发。所以**没有修规则，把 case 留在结果里**。它对应的是签名检测
的结构性边界：只看「请求里有什么词」，不看「这个字段本来就该装 HTML」。
真要修，需要的是上下文（字段级白名单 / 响应码 / 来源可信度），不是再加一条正则。

### 2.6 Brute Force 补强：从「命中 0」到窗口告警 8/8（v1.7）

§2.4 里最难看的一行是 **Brute Force 窗 7,181 条请求、命中 0**。它不是规则
数量不够，而是**判据类型缺失**：签名只看「这一条请求里有什么词」，看不出
「同一个 IP 在四十分钟里试了几千次密码」。补法是加一条声明式窗口规则
[`rules/http_brute_force.yaml`](../rules/http_brute_force.yaml)：

```
同一源 IP · 60s 滑动窗口 · 登录端点请求数 >= 30 → 1 条告警，命中后静默 300s
```

**阈值 30 不是照着周四调出来的。** 先在两个官方标注为全良性的工作日上量
「正常用户在任意 60s 窗口内最多访问多少次登录页」：

| 标定语料 | HTTP 请求 | 登录端点请求 | 源 IP 数 | 60s 峰值 | 阈值 30 下告警 |
|---|---:|---:|---:|---:|---:|
| 周一（零攻击工作日） | 54,732 | 64 | 9 | **4** | **0** |
| 周二（纯 HTTP 良性语料） | 48,345 | 57 | 10 | **4** | **0** |

两天峰值都恰好是 4，阈值 30 留了 7.5 倍余量。这是一个可以直接算的**阈值
不敏感区间**：良性峰值 4、周四攻击源峰值 153，所以阈值取 `[5, 153]` 中任意
整数，都不会在良性日产生告警、也仍能在周四触发。选 30 只是取一个常见的
整数，不是拟合出来的最优值。

**全量复测（三份 PCAP 各跑一遍，未切片）**：

| 数据集 | 登录端点请求 | 60s 峰值（分组） | 窗口告警 | 告警 TP | 告警 FP | BF 窗覆盖 |
|---|---:|---:|---:|---:|---:|---:|
| 周一（全良性） | 64 | 4（`192.168.10.5`） | 0 | 0 | 0 | 0/0 |
| 周二（全良性） | 57 | 4（`192.168.10.5`） | 0 | 0 | 0 | 0/0 |
| **周四（Web 攻击日）** | **5,582** | **153**（`172.16.0.1`） | **8** | **8** | **0** | **1/1** |

周四 8 条告警的时间区间是 `20:21:41 ~ 21:00:11`（采集器本地墙钟；换算成
ADT 即 `09:21 ~ 10:00`），**整段落在论文给的 Brute Force 窗内**，源 IP 全是
NAT 后的攻击源 `172.16.0.1`。8 条而不是 1 条，是 300s 静默期在 40 分钟攻击
里周期性解禁的结果，不是重复计数错误；窗口内请求数依次为 30 / 78 ×7。

**改进前 / 改进后对照**：

| | 改进前（v1.6，仅签名） | 改进后（v1.7，签名 + 频次窗口） |
|---|---|---|
| Brute Force 窗内请求命中 | **0 / 7,181**（逐请求） | 逐请求仍为 **0**（签名没变） |
| Brute Force 对应窗口告警 | **0** | **8 条，8 TP / 0 FP**，标注窗覆盖 1/1 |
| 纯良性两天新增告警 | 0 | **0**（新增判据没有引入告警级误报） |
| 逐请求主指标 | 检出率 9.56% / 精确率 95.31% | **完全不变**（v1.7 期间如此；v1.9 见 §2.9） |

> ⚠️ **这两列不能相加、不能互相替换。** 右侧是**告警（窗口）级**结果：
> 一次爆破的几千条请求合起来才是一次攻击，无法逐条标注「哪条该告警」。
> 所以 v1.7 发布时主混淆矩阵 `TP 853 / FN 8,072 / FP 42 / TN 47,143` 一个数没动，
> 9.56% 也不会因为补了这条规则变成好看的数字。**补的是判据类型，
> 不是把分数刷上去。** 评测脚本与粒度声明见
> [`bench/run_frequency.py`](run_frequency.py)，三份报告原文在
> [`bench/results/*_frequency.md`](results/)。
>
> v1.9 修归一化后主矩阵变成 `TP 855 / FN 8,070 / FP 42 / TN 47,143`（检出率 9.58%），
> 但那是**签名判据**的变化（§2.9），与本节的频次判据无关——**本节 8 条窗口告警
> 在 v1.9 复跑后仍然一字不差**。

复现：

```bash
python bench/run_frequency.py --pcap <Monday.pcap> \
    --labels bench/labels/cic_ids2017_monday_benign.json --calibrate
python bench/run_frequency.py --pcap <Thursday.pcap> \
    --labels bench/labels/cic_ids2017_thursday_web.json \
    --out bench/results/cic_ids2017_thursday_frequency.md
```

**仍然存在的局限（没有藏）**：

- 解析器只还原客户端方向，**不提取响应状态码**。所以这条判据靠「请求频次」
  而非「连续 401/403」——低频慢速爆破（每小时几次）仍抓不到，需要响应侧
  解析或更长的窗口，而不是把阈值调到 5。
- `match` 用 URI 里的 `login` 限定范围。换个不叫 login 的认证端点就失效；
  这是可解释的取舍（避免把全天所有请求一起计数），不是通用性声明。
- 只在 CIC-IDS2017 这一份 2017 年的数据集上验证过，不能外推到现代流量。

### 2.8 跨项目交叉评测：用 bypasslab 的绕过载荷打自己的规则（v1.8 起；下表数字为 v1.9 复跑）

前面 2.3–2.7 测的都是**别人打别人**的真实流量。这一节换一个问题：

> **专门为绕过检测而构造的载荷，这套规则认不认？**

语料来自 `bypasslab/internal/payloads`（228 条：corpus 112 / OWASP CRS 59 /
CRS 负样本 8 / hard 18 / hard2 12 / holdout 19），其中 192 条攻击、36 条良性。
这些载荷的难点是照着检测逻辑设计的——URL 编码、双重编码、大小写扰动、
注释拆分——正好压在最容易写坏的归一化层上。

**口径三条**（缺一条数字就不可信）：

1. **只测签名规则**：20 条参与；3 条窗口/阈值规则要多次事件才成立，单条样本
   无法评测，**不参与不等于漏检**。
2. **能力边界不进分母**：本工具没有 RCE / SSRF / 扫描器指纹规则，这三类记
   `unsupported` 并排除在检出率之外。把「没有这个能力」算成「检出率 0%」，
   是拿分母惩罚自己。
3. **事件构造复用生产代码**：直接调 `collectors.pcap._build_event()`，raw 拼接、
   `normalized` 归一化、uri 抽取与线上同一份代码。

| 类别 | 在检测范围 | 攻击样本 | 检出 | 检出率 |
|---|---|---:|---:|---:|
| `sqli` | ✅ | 50 | 23 | **46.0%** |
| `xss` | ✅ | 32 | 20 | **62.5%** |
| `path-traversal` | ✅ | 20 | 13 | **65.0%** |
| `deserialization` | ✅ | 15 | 9 | **60.0%** |
| `rce` | — | 49 | — | 不计入（无规则） |
| `ssrf` | — | 18 | — | 不计入（无规则） |
| `scanner` | — | 8 | — | 不计入（无 UA 指纹规则） |

**检测范围内合计 65/117 = 55.6%**（v1.8 首次评测时为 58/117 = 49.6%，差的 7 条
全部是 §2.9 修掉的 form 编码缺口）；良性 36 条中误报 **1** 条
（`CRS-941100-05`，Referer 里带 `<script>`——CRS 认为不检、我们检）。

**分语料集看，差异比总分更有信息量**：

| 语料集 | 攻击 | 检出 | 检出率 | 说明 |
|---|---:|---:|---:|---|
| `corpus` | 84 | 45 | 53.6% | 项目自己迭代过的 |
| `crs` | 59 | 12 | **20.3%** | OWASP 第三方基准，没针对它调过 |
| `hard` | 18 | 5 | 27.8% | 加固样本 |
| `hard2` | 12 | 6 | 50.0% | 第二轮加固 |
| `holdout` | 19 | 7 | 36.8% | 冻结的泛化集（只报总数，见下） |

> **55.6% 和 99.07% 不矛盾，但也不能互相替代。** 99.07% 是真实数据集里
> 「带载荷的攻击请求」——真实攻击者的载荷目标是**打进应用**；
> 55.6% 是「专门为骗过检测器构造的载荷」——目标是**绕过规则本身**。
> 两者难度不同。这个数字的作用不是给检测器打分，而是**指出规则和归一化
> 具体烂在哪一层**。注意 `crs` 那一行几乎没动（12/59）：v1.9 修的是编码层，
> 第三方基准里缺的是**判据形态**（无引号恒真式等），不是编码。

**根因分三类，性质完全不同**：

1. **归一化缺口（v1.9 已修）**：`normalize()` 只做 `unquote()`，**不处理 `+`**。
   而 query 与 `application/x-www-form-urlencoded` body 里 `+` 的语义就是空格，
   `id=1+UNION+SELECT+...` 归一化后仍是 `1+union+select`，规则里的 `union select`
   匹配不到。修法见 §2.9，效果 **49.6% → 55.6%**、SQLi **16/50 → 23/50**——
   **这 7 条一条规则都没改**，只是把同一语义的另一种编码解出来。
2. **规则覆盖缺口（要加规则）**：如 `1234 OR 1=1`（`CRS-942100-01`），
   `http-sqli-boolean-blind` 只认带引号的 `' or '1'='1` 形态。v1.9 之后
   这一类的占比反而更显眼了——编码层已经没有借口，剩下的就是判据没写。
3. **能力缺口（不是漏检）**：RCE / SSRF / 扫描器指纹共 75 条，没有对应规则。

> **第 1 类是「先量化、再单独修」的范例。** v1.8 首次跑出 49.6% 时只做归因
> 不修，理由是它会改动已发布的全部指标（9.56% / 98.84% / 误报 4 条），
> 必须带着三份 CIC 全量回归单独做一次。v1.9 就是这么做的：三份全量重跑、
> 告警级复测、误报一条没增（见 §2.9）。

> **holdout 纪律**：`bypasslab` 的 Holdout 是冻结语料，那边明确规定只报总数、
> 不报明细（否则读代码的人会针对性改规则）。本报告同样不列它的漏检 ID，
> 只给 7/19。

复现：

```bash
cd ../bypasslab && go run ./cmd/export -out out/corpus_full.json
cd ../sentinelwatch && python bench/run_crosscheck.py \
    --corpus ../bypasslab/out/corpus_full.json \
    --out bench/results/crosscheck_bypasslab.md
```

### 2.9 v1.9：修 form 编码的 `+` 解码（带三份全量回归）

§2.8 定位到「`normalize()` 不解 `+`」这个缺口后，本轮把它修了。这一节记录
**改了什么、为什么这么改、三份全量重跑的结果**。

**改动只有一处**：`collectors/pcap.py` 新增 `_judgement_text()`，为归一化视图
单独构造输入——请求行的 **query 部分**与 Content-Type 为
`application/x-www-form-urlencoded` 的 **body** 里，字面 `+` 换成空格。

三个设计约束（都有测试守着，见 `tests/test_pcap.py` 与 `tests/test_crosscheck.py`）：

| 约束 | 为什么 |
|---|---|
| **只动 query 与 form body** | `+` 在 path、Header、JSON body 里是字面加号。整段 replace 会把 `/a+b` 改成 `/a b`，那是另一种失真 |
| **必须在 `unquote()` 之前换** | 反过来写，`%2B`（真正的加号）会先被解码成 `+`、再被误换成空格，语义被伪造 |
| **`raw` 一个字不动** | 判据可以归一化，证据不能。取证时看到的必须还是原始 `+` |

**逐请求指标：一升零降**

| 指标 | v1.8（修复前） | v1.9（修复后） |
|---|---|---|
| 周四 TP / FN | 853 / 8,072 | **855 / 8,070** |
| 周四 FP / TN | 42 / 47,143 | **42 / 47,143（未变）** |
| 周一 / 周二 FP | 3 / 0 | **3 / 0（未变）** |
| 整体检出率 | 9.56% | **9.58%** |
| 带载荷命中（863 条） | 853（98.84%） | **855（99.07%）** |
| 精确率（周四） | 95.31% | **95.32%** |
| 真实误报 | 4 / 150,262 | **4 / 150,262（未变）** |
| 检出率上界（窗放宽） | 9.70% | **9.73%** |

多抓到的 2 条都落在 SQLi 标注窗（9 条里命中 3 → 5），XSS 窗 850/1,735 与
Brute Force 窗 0/7,181 完全没动。**误报一条没增**——这是这次敢合入的前提：
一个检测改动提高检出的同时把误报带上去，就没资格叫"改进"。

**告警级指标：完全不变**

`http-login-brute-force` 匹配的是 `uri` 字段，不经过 `normalized`，所以窗口级
结果按预期应该不变——实测确认：

| | 周一 | 周二 | 周四 |
|---|---|---|---|
| 60s 峰值登录请求 | 4（未变） | 4（未变） | 153（未变） |
| 窗口告警 | **0** | **0** | **8（8 TP / 0 FP，未变）** |

**跨项目交叉评测：49.6% → 55.6%**

| | v1.8 | v1.9 |
|---|---|---|
| 检测范围内检出 | 58/117 = 49.6% | **65/117 = 55.6%** |
| SQLi | 16/50 = 32.0% | **23/50 = 46.0%** |
| OWASP CRS 子集 | 12/59 = 20.3% | **12/59 = 20.3%（未变）** |
| 良性误报 | 1/36 | **1/36（未变）** |

`crs` 子集一条没多抓，正好说明这个改动**不是万灵药**：它只解编码层，
第三方基准里缺的是判据形态（无引号恒真式之类），那要靠加规则。

**复现**：

- **规则覆盖**：`1234 OR 1=1` 这类无引号恒真式仍漏，是判据形态问题。

## 3. 暴露出来的问题

### 3.1 解析器把整个文件读进内存 → 7.7 GB 直接 OOM（已修）

`_iter_records()` 原来用 `Path(path).read_bytes()` 一次性读入全文件。自造的
8 包样本 1.5 KB 永远测不出，CIC 单日 7.7 GB 第一秒就打死。v1.4 改为按记录头
长度逐条读、新增 `iter_events()` 流式接口（活跃流空闲 300 秒即拼装释放）、
`_MAX_FRAME = 256 KB` 防止损坏文件触发 4 GB 读取。测试见 `tests/test_pcap.py`。

### 3.2 官方 `.pcap` 其实是 pcapng（已修）

头 4 字节 `0a0d0d0a`。原解析器报「未知 magic，请先 tcpdump 转换」——这条提示
把「能读这个文件」交给了本不想依赖的第三方工具。v1.5 把格式支持做进解析器
（零依赖）：SHB 判字节序并重置接口表、IDB 按 `interface_id` 记链路类型与
`if_tsresol`、EPB/PB 取包、SPB 跳过。**两个坑**：时间精度不是固定微秒
（`if_tsresol` 声明 10⁻⁹ 时按微秒算会偏 1000 倍）；链路类型是**按接口**的，
只记第一个接口会在多接口文件里静默少事件。验收用
`test_pcapng_matches_pcap_output`（同一批包两种容器逐字段相同）。

### 3.3 明细 CSV 攒在内存里（已修）

`run()` 原把每条请求攒成 dict 跑完才落盘，48,345 条真请求就是几百 MB。
改成边算边写，内存与文件大小解耦。与 §3.1 是同一类错误：**测试数据太小会掩盖
所有规模相关的问题**，一个在读入侧、一个在写出侧。

### 3.4 标注窗口与本地时区混用 → 周四首跑 TP/FN 全 0（已修）

首跑周四的结果是 `TP 0 FN 0 FP 895`，看起来像"检测器完全没用"。实际是：
标注窗按 UTC 基准存成 naive `12:20`，事件时间戳是采集器用
`datetime.fromtimestamp()` 渲染的**本地**墙钟 `20:20`，直接比大小差了 8 小时。
规则命中的 894 条真攻击全被记成误报。

这和之前 self_test 三版本全红是**同一个病根**，只是这次藏在真实标注文件里。
修法不是把 offset 从 3 改成 11（那等于把本机时区焊死，换台机器又红），而是
`AttackWindow.covers()` 统一在 epoch 上比较。`tests/test_bench_labels.py` 用
UTC / 上海 / 纽约 / 柏林四个子进程验证——**必须包含非 UTC 时区**，旧代码在
UTC 机器上恰好能过。

### 3.5 攻击源 IP 用了公网地址（已修）

见 §1.1。填 `205.174.165.73` 会让所有窗口一条都匹配不到。

### 3.6 结构性局限（未修，且不打算靠调参掩盖）

| 局限 | 实证 | 性质 |
|---|---|---|
| **Brute Force 检不出（v1.6）→ 已补强（v1.7）** | 7,181 条登录爆破请求，签名命中 0 | 曾判定为「判据类型缺失」，v1.7 补了 60s 频次窗口规则：周四 8 条窗口告警全部 TP、纯良性两天 0 告警，**但主矩阵一个数没动**，见 §2.6。剩余边界是解析器不看响应码、URI 限定 `login` |
| **编码后的合法富文本误报** | 4 条，全是广告竞价日志 | 归一化的固有代价，见 §2.5，**保留不修** |
| **只还原 HTTP** | 周二 FTP/SSH 爆破一个事件都没有 | 数据源覆盖范围，不是检测器 bug：同一场爆破在 `auth.log` 里可见（项目有 SSH 爆破阈值规则），换采集器就抓得到 |
| **阈值规则不进矩阵** | 一次爆破的 5 条失败请求无法逐条标注 | 粒度不同，硬混会让指标失去意义；v1.7 的解法是**另出一份告警级评测**，而不是把它们塞进主矩阵 |

> 「检不出」这一行保留着改进前的数字，是为了让人看清补强前后发生了什么。
> 它比报一个漂亮的总检出率更有价值：说明我清楚这套判据的边界在哪，
> 也清楚下一步该补什么，而不是靠加正则把分数刷上去。

### 3.7 一个选题问题（已处理）

CIC-IDS2017 是 2017 年的数据，Web 攻击是 SQLi / XSS / Brute Force，而最初 13 条
签名规则全是 Log4Shell（2021）/ Fastjson / WebShell——直接跑必然接近 0%，
但那个 0 说明的是「我在测一个规则没打算覆盖的东西」。v1.5 按
[`DATASETS.md`](DATASETS.md) 路线 A 补了 7 条 Web 攻击规则
（`rules/http_web_attacks.yaml`：SQLi 四类、XSS 两类、路径遍历），才有了 §2.4
的 98.84%。**扩规则是补短板，换数据集是回避短板。**

## 4. 复现方式

数据不进仓库（`.gitignore` 排除 `data/` 与 `out/`）。三份官方 PCAP 需要先过一次

```bash

python bench/run_benchmark.py \
    --pcap <Monday-WorkingHours.pcap> \

python bench/run_benchmark.py \
    --pcap <Tuesday-WorkingHours.pcap> \
    --labels bench/labels/cic_ids2017_tuesday_benign.json --out out/

python bench/run_benchmark.py \
    --pcap <Thursday-WorkingHours.pcap> \
    --labels bench/labels/cic_ids2017_thursday_web.json --out out/

# 3) 复核时区偏移（按端口 SYN 突增段反推）
python tools/probe_window.py <Tuesday-WorkingHours.pcap> 21 22

# 4) v1.7 频次窗口规则：先用纯良性语料标定，再跑攻击日
#    （告警级评测，产出 *_frequency.md，不与上面的逐请求矩阵混算）
python bench/run_frequency.py --pcap <Monday.pcap> \
```

产物：

- `out/bench_<name>.csv`：逐请求明细（ts / src_ip / method / host / uri / 期望 /
  攻击类型 / 命中规则 / TP-FN-FP-TN）

  标注灰色地带 + 误报归因。**这份报告会同步存档到 `bench/results/` 并随仓库提交**
  （`out/` 被 `.gitignore` 排除，不存档的话 clone 下来就看不到复核依据了）
- `bench/results/*_frequency.md`：v1.7 的**告警级**报告三份（阈值标定依据 +
  告警 TP/FP + 样例窗口），由 `bench/run_frequency.py` 直接产出
- `bench/results/README.md`：六份报告的索引与「为什么不提交 CSV」
