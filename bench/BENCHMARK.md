## 1. 评测口径（先定口径，再看数字）

数据集标签按 **flow** 打，本工具产出按 **HTTP 请求** 的事件。粒度不同，硬对齐
会算错。所以评测不使用数据集自带标签，而用显式声明的口径：

```
落在某攻击时间窗内 且 源 IP 为该窗的攻击源 IP  → 应检出（positive）
其余请求                                        → 应放行（negative）
```

两个条件缺一不可。只按 IP 判会把攻击者在非攻击时段的正常流量算成攻击，人为
抬高检出率；只按时间窗判会把同网段正常用户算成攻击，人为抬高误报率。

**只有签名规则进混淆矩阵。** 阈值规则（窗口聚合）是另一个粒度：一次爆破的
5 条失败请求，无法逐条标注"哪条该告警"。混进来算，指标就没有意义了。

## 2. 结果

### 2.1 脚本自检（合成样本，已验证 ✅）

这不是数据集结果，是"评测脚本本身对不对"的证明——如果连脚本都有 bug，
跑出来的数就没意义。用 `tools/pcapgen.py` 的演示样本，标注为
「2 条正常 + 3 条攻击」：

```bash
$ python bench/run_benchmark.py --self-test
自检结果
  事件 5 条：TP=3 FN=0 FP=0 TN=2
  检出率 100%，误报率 0%
[+] 自检通过：脚本的判定与计数逻辑正确，可以拿去跑真实数据集
```

| 项 | 值 |
|---|---|
| 事件数 | 5 |
| 混淆矩阵 | TP 3 / FN 0 / FP 0 / TN 2 |
| 判定 | 与标注完全一致 |

### 2.2 解析器吞吐标定（合成样本，已测 ✅）

跑真实数据集之前先量一下"7.8 GB 要跑多久"，否则"要不要跑全量"这个决定就是拍脑袋。

```bash
$ python tools/bench_throughput.py 48
解析器吞吐标定（合成样本）
  样本体积   48.0 MB
  解析事件   136073 条
  耗时       3.21 s
  吞吐       15.0 MB/s   （42436 请求/s）
  推算真实数据集：
    周四（含 Web 攻击）        7.8 GB → 约 9 分钟
    周一（纯良性）            11.0 GB → 约 13 分钟
```

**这不是数据集结果**，样本是 `tools/pcapgen.py` 合成的。它回答的只是
"解析器本身有多快"，和检出率无关。写在这里是因为它决定了一个实际决策：

- 解析不是瓶颈，7.8 GB 大约 9 分钟。**所以"数据太大跑不动"不成立**，
  真正的时间成本在下载那 7.8 GB，不在解析。
- 合成样本按"一条请求一个独立 5 元组"造。如果复用少数几条流，绝大多数字节
  只进 TCP 重组缓冲区、不当场解析，量出来的吞吐会虚高数倍——这是第一版
  标定脚本踩的坑，记在这里免得后人重踩。

真实数据集跑完之后，同一张表要补上**真实流量**的吞吐（真实 pcap 帧更大、
TLS 占比更高，按字节算通常比这个数快）。

#### 周二跑出来的三个事实

```
文件：Tuesday-WorkingHours.pcap（pcapng 容器，11,048,283,608 字节）
跨度：2017-07-04 19:56:02 ~ 2017-07-05 04:00:30（约 8 小时）
HTTP 请求：48,345 条      包数：约 1,900 万（≈ 390 包/请求）
签名规则命中：0 条        FP 0 / TN 48,345
单线程全量耗时：113.9 秒   → 96.99 MB/s
```

1. **误报率 0.0000%（0/48,345）**。参与判定的 10 条签名规则（Log4Shell JNDI、
   Fastjson autoType、WebShell 特征、SQLi ×4、XSS ×2、路径遍历）在一天的
   真实业务流量里一条都没误报。这个数字的价值在于**语料是第三方给的**——
   拿自己造的良性流量算误报率等于自己出题自己答。
2. **吞吐 96.99 MB/s**，比合成样本标定的 15 MB/s（见 §2.2）快了 6 倍。原因不是
   优化了，是合成样本的构造方式更"毒"：每条请求占独立五元组、请求密集、需要
   频繁建流拆流。真实流量里大量是响应包与非 HTTP 流量（SSH/FTP/扫描），
   单包处理成本低。**两个数都对，但含义不同**：合成样本测的是"最坏情况下的
   建流开销"，真实数据集测的是"这一天的流量组合"。
3. **请求/s 只有 424**，别拿这个数当性能指标。CIC 这一天平均 390 个包才出一条
   HTTP 请求（48,345 请求 / 约 1,900 万包），瓶颈根本不在检测逻辑，在"读包"。

#### 周二为什么没有检出率

这一天的攻击是 FTP-Patator（约 09:20–10:20）与 SSH-Patator（约 14:00–15:00），
打的是 21/22 端口，**不产生任何 HTTP 请求**。本工具流量侧只还原 HTTP，所以这一天
在"按 HTTP 请求"的事件粒度下天然全是负样本。

这一点写在这里而不是藏起来：**漏掉 FTP/SSH 爆破不是检测器的 bug，是数据源覆盖
范围的问题**——同一场爆破在 `auth.log` 里是可见的（项目有 SSH 爆破阈值规则），
换个采集器就抓得到。这正是"日志 + 流量双数据源"这个设计要说明的事。

检出率必须等周四（Web 攻击段）。

#### 跑之前先修的两件事（都是真实数据逼出来的）

| 问题 | 症状 | 修法 |
|---|---|---|
| 官方文件其实是 pcapng | `未知 magic 0a0d0d0a`，一个事件都出不来 | v1.5 给 `collectors/pcap.py` 加了原生 pcapng 解析（SHB/IDB/EPB + `if_tsresol`），不再需要 tcpdump 转格式 |
| 明细 CSV 攒在内存里 | 自造样本 5 条请求看不出来；真数据几万条就要占几百 MB，几十万条直接 OOM | `run()` 改成边算边写，内存占用与文件大小解耦 |

## 3. 已暴露的问题（这部分是真的）

跑基准的第一件事不是拿到数字，是发现"自造样本永远发现不了的问题"。
目前已经暴露 3 个，并且全部修了：

### 3.1 解析器把整个文件读进内存 → 7.7 GB 直接 OOM（已修）

`_iter_records()` 原来用 `Path(path).read_bytes()` 一次性读入全文件。
自造的 8 包样本 1.5 KB，永远测不出这个问题；CIC 单日 7.7 GB，
进程第一秒就被打死。

修法（v1.4）：

- `_iter_records()` 改为逐条记录从文件读——PCAP 记录头自带长度，天然可分帧，
  流式读不需要任何妥协；
- 新增 `iter_events()` 流式接口：一条流空闲超过 300 秒就当场拼装产出并释放，
  **内存上界由"活跃流数量"决定，不再由文件大小决定**；
- 加 `_MAX_FRAME = 256 KB` 上限：文件损坏导致 `incl_len` 是垃圾值时直接报错，
  而不是尝试 `f.read(4GB)`；
- `parse_file()` 保留（中小文件、需要全局时间序），内部行为不变。

覆盖这三点的测试：`tests/test_pcap.py` 里的
`test_iter_events_matches_parse_file`、`test_iter_events_keeps_all_requests_in_keepalive_flow`、
`test_iter_events_releases_idle_flows`、`test_iter_records_rejects_absurd_frame_length`。

**这个 bug 值钱的地方**：它只有在"文件比内存大"时才出现。说明**换一把尺子
才能看见自己的剑有多长**——这正是做公开数据集评测的意义，与检出率高低无关。

### 3.2 真实数据第一眼：文件根本不是 pcap（已修）

官方给的 `Tuesday-WorkingHours.pcap` 头 4 字节是 `0a 0d 0d 0a`——**pcapng**，
不是 libpcap。原来的解析器直接报 `未知 magic 0a0d0d0a` 并提示"请先 tcpdump 转换"。

这条提示本身就是个错误设计：它把"能读这个文件"的前提，交给了我本来不想依赖的
第三方工具。v1.5 的做法是**把格式支持做进解析器**（标准库，零依赖）：

| 块 | 作用 | 处理 |
|---|---|---|
| SHB `0x0A0D0D0A` | 声明本 Section 的字节序 | 读字节序魔数决定 `<` / `>`，并重置接口表 |
| IDB `0x00000001` | 每个接口的链路类型 + 时间精度 | 按 interface_id 记 linktype 与 `if_tsresol` |
| EPB `0x00000006` | 实际数据包 | 拆 ts_high/ts_low，按接口精度换算 |
| PB `0x00000002` | 已废弃的老式包块 | 一并支持，老文件还会出现 |
| SPB `0x00000003` | 无时间戳的简单包块 | 跳过（没有时间戳就没有事件时间） |

**最容易踩的两处**：① 时间精度不是固定微秒，`if_tsresol` 声明成 10⁻⁹ 时按微秒算
会让时间偏 1000 倍，症状是"攻击窗对不上"而不是"报错"；② 链路类型是**按接口**的，
只记住第一个接口的实现在 SLL+Ethernet 混抓的文件上会静默少事件。

验收标准是"容器换了，检测结果不能变"：`test_pcapng_matches_pcap_output` 用同一批包
分别写 pcap 和 pcapng，要求解析出的事件逐字段相同。

### 3.3 明细 CSV 攒在内存里（已修）

`run()` 原来把每条请求攒成一个 dict 放进 `rows`，跑完才落盘。5 条自造样本看不出
问题，48,345 条真请求就是几百 MB，如果碰上百万请求级别直接 OOM。

改成边算边写之后，内存占用与文件大小解耦。这条和 §3.1 是同一类错误：
**"我的测试数据太小"会掩盖所有规模相关的问题**——只不过一个是读入侧，一个是写出侧。

### 3.4 预计还会暴露的（等周四验证）

按已知边界推测，跑 CIC 周四时大概率会撞上这些（`README` 的"已知限制"里已列，
此处是"等实测确认"清单）：

| 预期问题 | 为什么会撞上 | 是 bug 还是边界 |
|---|---|---|
| chunked / gzip body 解析不到 | 只按 `Content-Length` 取体 | 边界（已在 README 声明） |
| 非 80 端口的 HTTP 被当流量丢弃 | 解析器不按端口过滤，但 CIC 有 8080 服务 | 待确认 |
| 大量 TCP 握手/挥手空包 | 数据集混杂全部流量 | 应静默跳过（已实现，需确认不崩） |
| 攻击类型不重叠导致检出率极低 | CIC 是 2017 年数据，没有 Log4Shell | **不是 bug，是选题问题**，见下 |

### 3.5 一个前置的选题问题（已处理）

CIC-IDS2017 的 Web 攻击是 **SQLi（21）/ XSS（652）/ Brute Force（1507）**，
而当时 13 条签名规则全是 **Log4Shell（2021）/ Fastjson / WebShell**。
直接跑，检出率会接近 0——但这个 0 说明的是"我在测一个规则没打算覆盖的东西"，
不是"检测器不行"。

**已按 `DATASETS.md` 的路线 A 处理**：v1.5 补了 7 条 Web 攻击规则
（SQLi 四类 / XSS 两类 / 路径遍历，见 `rules/http_web_attacks.yaml`）。
补完之后各段的预期：

| CIC 周四攻击 | 样本数 | 现在能测吗 | 说明 |
|---|---|---|---|
| Web Attack – SQL Injection | 21 | ✅ | UNION / 布尔盲注 / 时间盲注 / 元数据探测 四类判据都有 |
| Web Attack – XSS | 652 | ✅ | `<script` 与事件处理器注入覆盖主流 payload |
| Web Attack – Brute Force | 1507 | ❌ **检不出** | 表单爆破没有特征载荷，需要"响应码 + 频次"判据；而当前解析器只取客户端方向、不提取响应状态码 |

**那 1507 条"检不出"不要藏。** 它正好是方案要求的"至少 2 个暴露的局限"之一，
而且是**结构性**的：不是规则写得不够多，是**判据类型缺失**——签名匹配只能看
"请求里有什么词"，看不出来"同一个 IP 在 5 分钟内试了 500 个账号"。后者要阈值
规则 + 响应码，属于另一套判据体系。把这条讲清楚，比报一个漂亮的总检出率更有价值。

> 注：以上"能测"指**判据设计上覆盖**，不等于"实测一定命中"。真实数字必须等
> 数据跑出来，这里不做任何预估——预估本身就是一种编造。


## 4. 复现方式

```bash
# 1) 自检（不需要任何数据集，10 秒）
python bench/run_benchmark.py --self-test

# 2) 真实数据（先切一段 200 MB 跑通，别直接上 7.7 GB）
editcap -c 200000 Thursday-WorkingHours.pcap data/thu_200k.pcap
python bench/run_benchmark.py \
    --pcap data/thu_200k.pcap \
    --labels bench/labels/cic_ids2017_thursday_web.json \
    --out out/

# 3) 跑全量
python bench/run_benchmark.py \
    --pcap data/Thursday-WorkingHours.pcap \
    --labels bench/labels/cic_ids2017_thursday_web.json \
    --out out/
```

产物：

- `out/bench_<name>.csv`：逐请求明细（ts / src_ip / uri / 期望 / 命中规则 / TP-FN-FP-TN）
- `out/bench_<name>_report.md`：混淆矩阵 + 三个数 + 分攻击类型 + 标注灰色地带
